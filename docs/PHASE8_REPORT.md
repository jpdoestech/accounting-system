# Phase 8 Development Report — Inventory

## Completed

- `InventoryItem` model: each linked to two configurable GL accounts — an Inventory Asset
  account (where cost sits while unsold) and a COGS Expense account (where cost moves to
  when sold) — never hard-coded. Tracks `quantity_on_hand` and `average_cost`, maintained
  exclusively by `app/services/inventory.py`.
- `StockMovement` model: an immutable audit trail of every quantity/value change, created
  only by the inventory service, never edited afterward — same "no silent changes"
  principle used for `JournalEntry` since Phase 2. Each row records the item's running
  balance immediately after the movement.
- **Moving-average costing**: every receipt recalculates the item's average cost as a
  weighted average of what was on hand plus what came in; every issue draws quantity down
  at the *current* average without changing it. Verified by test with a genuine two-receipt
  weighted-average calculation: (100 × ₱10 + 50 × ₱13) / 150 = ₱11.00 exactly.
- **Integration with Purchases (Phase 5)**: a purchase bill line can now optionally carry
  an `item_id`. When it does, `post_bill()` debits the item's Inventory Asset account
  instead of the line's chosen expense account, and receives stock via the inventory
  service — after the journal entry posts successfully, never before, so a rejected posting
  never leaves an orphaned stock movement.
- **Integration with Sales (Phase 4)**: a sales invoice line can optionally carry an
  `item_id`. When it does, `post_invoice()` computes COGS from the item's *current* average
  cost (not the sale price), issues stock via the inventory service, and adds Debit COGS /
  Credit Inventory Asset lines to the **same** journal entry as the AR/Revenue/VAT lines —
  one atomic, balanced posting per invoice, not two separate entries. Selling more than is
  on hand is rejected before anything posts.
- Manual stock adjustments (for physical counts) reuse the exact same `receive_stock`/
  `issue_stock` functions sales and purchases call — no separate adjustment logic that could
  drift out of sync with the costing method.
- Full API for inventory items, stock movements (per-item history), and manual adjustments.
- Frontend: Inventory Items view (with live stock value = qty × avg. cost), and the Sales
  Invoice / Purchase Bill line forms both gained an optional item picker.

## Database Changes

Migration `60df4e1460a5_phase8_inventory` adds `inventory_items` and `stock_movements`, plus
nullable `item_id` FK columns on `purchase_bill_lines` and `sales_invoice_lines`.

**Same SQLite/Alembic issue as Phases 4–5, fixed proactively again:** the autogenerated
migration used plain `op.create_foreign_key(...)` for the two new FK columns on existing
tables, which SQLite rejects. Since this exact failure is now documented from three earlier
phases, I edited the migration to use `op.batch_alter_table(...)` before ever running it —
verified with a full `rm -f dev.db && alembic upgrade head` from empty, running all eight
migrations (Phases 1–8) in sequence without error.

## Tax/Accounting Rules Added

None — inventory doesn't introduce tax logic. VAT/withholding on an inventory-tracked
purchase or sale line still goes through the same Phase 3 tax engine exactly as before;
only the debit/credit side for the item's own cost changed.

## Known Issues

- Moving-average costing only — no FIFO or specific-identification costing method. The spec
  mentions costing methods generically; average cost is the simplest to implement correctly
  and is a legitimate BIR-acceptable method, but a business requiring FIFO would need a
  different (more complex) `StockMovement` consumption model.
- No low-stock alerts, reorder points, or purchase-order-driven replenishment — this phase
  covers quantity/cost tracking and GL integration only, not procurement planning.
- No item categories, variants (size/color), or serial/lot tracking — a flat item list with
  one SKU per row.
- A negative stock adjustment (`quantity < 0`) is rejected at zero on-hand the same as an
  oversell would be, but there's no UI for stock adjustments yet — the API endpoint exists
  and is used by tests, but no frontend form calls it (a reasonable Phase 8.x addition
  alongside a proper "physical count" workflow).
- COGS is computed and locked in at the moment of sale using whatever average cost was on
  file *then* — if a business voids/reverses a sale later (not yet supported — see Phase
  4/5's known issues on reversal), the corresponding stock movement and COGS entry would
  need explicit un-doing, which doesn't exist yet.
