# Phase 4 Development Report — Sales

## Completed

- `Customer` model: master data for accounts receivable (name, TIN, address, contact,
  payment terms).
- `SalesInvoice` / `SalesInvoiceLine` models: Draft → Posted → (Void reserved for later)
  lifecycle. An invoice is editable while Draft and immutable once Posted — the same
  no-silent-changes principle as journal entries (Section 117).
- Sales posting service (`app/services/sales.py`) that **composes** the accounting engine
  (Phase 2) and tax engine (Phase 3) rather than reimplementing either:
  - `create_draft_invoice()` computes each line's amount and, if the line has a
    `tax_rule_code`, calls the tax engine's `calculate_tax()` to get the tax amount —
    using the invoice date, so a draft that sits around across a rate change still shows
    (and later posts with) whatever rate is correct for its own date.
  - `post_invoice()` builds a balanced journal entry — Debit AR for the grand total, credit
    each revenue account for its line subtotal, credit Output VAT Payable for the tax total
    — and hands it to the accounting engine's `post_journal_entry()`. This is the **only**
    place a sales invoice's journal entry gets created; no new posting logic was written for
    Phase 4, only composition of what Phases 2–3 already built and tested.
- Business-configurable control accounts: `BusinessSettings.ar_account_id` and
  `.output_vat_account_id` — which accounts to post AR and Output VAT to are data, not a
  hard-coded account code, consistent with the project's core "configuration over
  hard-coding" requirement. Posting fails with a clear error if these aren't set, rather
  than guessing.
- A posted invoice cannot be posted again, and posting fails clearly if there are no lines,
  if the business hasn't configured its control accounts, or if the underlying period is
  closed (inherited automatically from the accounting engine — no new code needed for that
  check).
- API endpoints for customers (create/list) and sales invoices (create draft/list/get/post).
- Frontend: Customers view, Sales Invoices view (create draft with multi-line entry + tax
  rule selection, list with Post action), and Business Settings extended with AR/Output VAT
  account pickers.

## Database Changes

Migration `618141e2777f_phase4_sales` adds `customers`, `sales_invoices`,
`sales_invoice_lines`, and two nullable FK columns on `business_settings`
(`ar_account_id`, `output_vat_account_id`).

**A migration issue caught and fixed before this report was written:** Alembic's
autogenerated migration used a plain `op.create_foreign_key(...)` to add the two new FKs to
the already-existing `business_settings` table. SQLite doesn't support `ALTER ... ADD
CONSTRAINT`, so `alembic upgrade head` failed outright with
`NotImplementedError: No support for ALTER of constraints in SQLite dialect`. Fixed by
switching that part of the migration to `op.batch_alter_table(...)`, which recreates the
table under the hood (SQLite's supported copy-and-move strategy) — verified afterward with
a full `rm -f dev.db && alembic upgrade head` from an empty database, running all four
migrations (Phases 1–4) in sequence without error.

**Passed:** 25/25 automated tests, live smoke test, frontend build. **Failed:** the

## Known Issues

- No invoice void/cancel workflow yet — only Draft → Posted exists. Reversing a *posted*
  invoice would need to go through the accounting engine's `reverse_entry()` plus a
  corresponding invoice-status change; not built this phase since no test scenario needed it
  yet.
- No automatic invoice numbering — the user types the invoice number by hand.
  `BusinessSettings.invoice_number_prefix` exists (from Phase 1) but nothing generates the
  next number from it yet; a reasonable Phase 4.x addition.
- No partial payments / AR aging yet — an invoice is either unpaid (Posted, sitting in AR)
  or the business handles collection outside the system. Payment application belongs to a
  later phase (cash receipts against AR).
- No PDF/printable invoice generation — this phase is the accounting/tax correctness layer,
  not the customer-facing document; BIR-compliant invoice printing is a Phase 7 concern.
- Sales invoice lines currently only support one tax rule per line (or none) — no
  multi-tax-component lines (e.g. VAT + a separate percentage tax on the same line), which
  PH tax rules sometimes require. Would need the tax engine's calculation to accept a list
  of rule codes; not needed by anything tested so far.
